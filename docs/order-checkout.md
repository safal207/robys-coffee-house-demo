# Checkout, QR и будущая POS-интеграция

## Что работает сейчас

Меню и Smart Choice используют общий черновик с группами товаров, количеством и выбранными вкусами. `openOrderCheckout({ draft, language, returnFocus })` из [`src/order-checkout.js`](../src/order-checkout.js) показывает состав, сумму, номер и локально сформированный QR. Сканирование открывает [`cashier.html`](../cashier.html) с тем же составом; гость показывает его сотруднику и оплачивает заказ на кассе.

Это **статический сценарий оплаты у кассы**. Сайт не отправляет заказ сотруднику, не создаёт запись в POS и не принимает оплату. Надпись «Ожидает оплаты на кассе» описывает следующий шаг, а не подтверждённый сервером статус. Подготовка после оплаты — инструкция сотруднику; сайт не узнаёт, началась ли она.

Номер создаётся через `crypto.getRandomValues`. Неизменённый черновик повторно использует сохранённый ticket; изменение состава или количества создаёт другой. `localStorage` разделяет последнюю запись между вкладками, `sessionStorage` и память обеспечивают fallback. При quota-error pending-marker сохраняет номер после перезагрузки, не затирая более новую запись другой вкладки. Это не серверный реестр заказов.

## Формат и проверка QR

[`src/order-ticket.js`](../src/order-ticket.js) кодирует wire **v2** в base64url в URL-фрагменте `cashier.html#payload`. Внутренняя модель ticket остаётся `version: 1`. Декодер поддерживает прежний wire v1.

Бинарный v2 содержит версию, 20 ASCII-символов ID, 6 байт времени создания, язык, 4 байта отпечатка каталога и группы. Группа содержит количество и число компонентов; компонент — индекс товара, количество и индекс вкуса. Цены, персональные данные, оплата и статусы подготовки не передаются.

Проверяются канонический base64url, длина payload ≤ 2 000 символов, URL ≤ 2 250, максимум 64 группы и 8 компонентов в группе, целые количества 1–99 и общий предел 99 для одного товара, известные ID и допустимые обязательные вкусы. Обрезанные/лишние байты и несовместимый каталог отклоняются. Отпечаток каталога — проверка совместимости индексов, **не подпись и не подтверждение подлинности заказа**.

Сумма заново рассчитывается по [`menu-catalog.js`](../menu-catalog.js), а не по данным QR. На статическом сайте это каталог загруженной версии приложения; offline-копия может отставать от кассы. Изменение цены не блокирует старый QR, изменение структуры каталога требует создать новый. Человек может скопировать или изменить QR; он не подтверждает оплату.

## Подключение POS в будущем

`buildPosOrderRequest(ticket)` формирует только `{ schemaVersion, clientRequestId, createdAt, groups }`. Функция не делает сетевого запроса. Адаптер подключается отдельно:

1. Сервер принимает состав, повторно проверяет ID, вкусы, количество, наличие и цены по своему каталогу. Клиентское время не считается доверенным. Сервер возвращает собственный ID и итоговую сумму; изменившуюся сумму нужно показать перед оплатой.
2. `clientRequestId` используется как ключ идемпотентности: повтор не создаёт второй заказ, тот же ключ с другим составом отклоняется. Короткий отображаемый номер не заменяет полный серверный ID.
3. POS/платёжный провайдер сообщает результат серверу. Сервер проверяет подпись webhook, сумму, валюту и связь с заказом, обрабатывает повторы событий. Для наличной оплаты требуется авторизованное действие кассира/POS.
4. Только серверное подтверждение переводит заказ в `paid`; действие POS/сотрудника — в `preparing`. Браузер читает разрешённый серверный статус. QR, URL, localStorage и клиентская кнопка не могут назначать эти состояния.

## Ограничения и проверка

GitHub Pages размещает клиентские файлы этого демо; backend, POS, webhook, авторизация кассира, учёт наличия и подтверждение оплаты здесь не реализованы. Секреты POS/платёжного провайдера должны храниться на отдельном сервере. Без доступного хранилища долговременное сохранение номера невозможно; без предварительно загруженного кеша offline-страница недоступна.

После пересборки запустите `npm run test:ordering`. Тесты проверяют пары/вкусы/количество, восстановление номера, строгий декодер, совместимость форматов, программное сканирование реального SVG и offline-маршрут кассира. Проверка камерой и реальные desktop/mobile сценарии дополняют эти тесты.
